# PLAN 独立审查：Round 1

结论：**NEEDS_CHANGES**

审查范围：完整读取 `research/report.md` 与 `PLAN.md`，并读取 `config.yml`；按 A–E、P1–P5、PLAN 必备形状和文档质量审查。`check-plan.py` 退出 0，只代表结构检查通过，不覆盖以下语义问题。未重跑调研命令。

Finding 统计：阻断 2，重要 5，次要 2，共 9 条。

## Findings

### 阻断

#### B1. 多个 spec 不满足 P2 独立回滚

- PLAN `01-device-safety` 的“独立产出”只声明自身回滚范围（第 56 行），但 `02-offline-quality-gate` 又把 `tests/test-device-safety.sh` 固定纳入门禁，并规定后续 spec 持续向该入口注册测试（第 62–64 行）。回滚 `01` 会使已合入的 `02` 失去被消费文件；同理，回滚 `03`/`04`/`05` 会影响其后消费契约或注册测试的 spec。
- PLAN 对 `02`–`07` 没有逐项说明回滚边界、兼容期或降级行为，无法证明“回滚它不牵连已合入的其他 spec”。
- 这直接违反 P2；七片不能按现状全部成立。应为每片写明可执行的回滚路径，并把门禁注册、接口兼容和工件所有权设计成不要求修改/回滚其他已合入 spec。

#### B2. `06-canonical-core-adapters` 粒度明显超过 P5，切口也不稳定

- PLAN `06`（第 90–96 行）一次收敛 feature 探测/解析、manifest schema、branch check、session hook、verifier 调度、backend 注册、三套 wrapper/上下文/兼容链接，并要求旧入口全部回归。
- report “工程形态与单一真相源”“重复代码与扩展点”（第 5–9、31–35 行）支持做这些工作，却不支持把它们合成一个原子改动。该产出跨多个接口和文件族，人审全部产出无法可信地控制在 1 小时内；同时 manifest、registry、hook、verifier 一起变化，会让接口契约在片内反复移动。
- 应沿稳定接口拆成可独立验收的垂直片，例如“registry/resolver + manifest”“session adapter”“verifier adapter”，每片保留旧入口兼容回归；不能只按文件层横切。

### 重要

#### I1. 依赖图无环，但缺少可核对的“消费 ↔ 产出”签名

- PLAN 依赖图（第 106–121 行）是 DAG；但 spec 表和详情没有显式“消费”字段。
- `04` 依赖 `03`，`06` 同时依赖 `03`/`04`/`05`，却没有写明消费者调用哪个具体接口、参数/输出/退出码如何对应。`harness_adb_run <mode> <serial> -- <args...>`、`harness_validate_feature_name <name>`、`harness_session_state_path <project-id> <session-id>` 只有命令外形，没有 stdout/stderr、返回码、错误分类、路径格式等契约；`06` 也未明确逐项消费这些签名。
- 因而 C 维“消费与产出签名匹配”当前不可验证，也削弱 `03 → 04 → 06`、`05 → 06` 的稳定切口。需补依赖契约表并写死完整 shell 协议。

#### I2. report 指出的运行时资源租约/锁没有处置

- report 第 27–29 行指出，“单一客户端写入”和 contract 不漂移仍只是文字约定，源码、构建输出、设备/CVD 均没有租约/锁。
- PLAN `05` 只做 session 文件隔离，`资源冲突`（第 123–129 行）只规定七个实施 spec 串行和测试使用 mock；唯一 serial 也不能阻止两个真实会话选择同一设备。
- 这既是 A 维遗留项漏处置，也是 C 维资源冲突不完整。应明确实现哪类租约/锁，或明确排除并记录真实并发风险及验收边界。

#### I3. report 的 build/CVD 超时缺口与覆盖率未知项未明确处置

- report 第 19–23 行把 ADB、CVD、build 都列为缺少命令级超时/恢复策略；PLAN `04` 的具体工作只落实公共 ADB 执行器，未说明 build/CVD 是后续工作还是明确不在范围。
- report 第 54–60 行的覆盖率未知项没有在任何 spec、全局约束或“待人审”中出现。PLAN 已正确处置真机、跨平台、攻击/并发探针和三套架构选择，但仍未覆盖这一项。
- 应逐项给出“实现 / 记录为非目标 / 后续 spec”的明确去向，不能靠全局泛称“超时可配置”代替归属。

#### I4. 高不确定性的 `05` 没有优先，排序理由不足

- report 第 56–59 行明确说明路径逃逸、软链跟随和双会话竞争尚未用攻击/并发探针复现；这是已知高不确定性。
- PLAN `05` 只依赖 `02`，却在顺序理由（第 121 行）中无技术依据地安排到 `04` 之后。`01` 先处理单点安全风险、`02` 先建立门禁是合理的；其后应优先消除 `05` 的未知，或写出晚排所依赖的具体证据。
- E 维目前只有“单点失败优先”通过，“高不确定性优先”未通过。

#### I5. `02` 的可选静态工具策略尚未成为可验收契约

- report 第 37–41 行说明当前环境缺少 ShellCheck、shfmt、actionlint 和秘密扫描工具。
- PLAN `02`（第 58–64 行）只说“采用明确安装/失败策略”，没有决定缺工具时本地门禁是失败、跳过还是降级，也未区分 CI 与开发机；但总验收又要求 `./scripts/check.sh --offline` 确定退出 0。
- 这会使同一验收命令随环境产生不同语义。应在 PLAN 固定缺工具行为、CI 安装/版本策略和输出语义。

### 次要

#### M1. “P0”是未标注的严重度推断

- PLAN 第 4、38、52–54 行称“两项 P0”；report 第 11–17 行只称“高优先级缺陷”，没有 P0 定义或定级记录。
- 技术事实和优先处理顺序有出处，但 P0 标签是计划判断。应改回 report 用语，或标明为本计划的风险定级，而非上游事实。

#### M2. `06` 新注册接口只覆盖成功路径

- PLAN `06` 第 94–96 行要求 fake client 仅靠新增注册目录即可被发现，但没有覆盖重复 `name`、缺键、非法 command/context、畸形四列 manifest 等失败路径。
- report 第 33–35 行支持消除硬编码扩展点；新扩展点仍需 fail-closed 的负向判据。可在拆分后的 registry/manifest spec 中补充。

### A–E 汇总

- A 溯源：⚠️ 七个 spec 均能回指 report，但租约/锁、build/CVD 超时、覆盖率未知未完整处置。
- B 粒度：❌ P1/P3/P4 基本成立；P2 未成立，`06` 明显不满足 P5，多个接口仅有名字没有协议。
- C 依赖：⚠️ 图无环；消费/产出签名不可完整核对；实施文件冲突已串行，但运行时资源冲突遗漏。
- D 目标一致性：⚠️ 各判据覆盖安全、门禁、契约、ADB、session、canonical core 和文档，且没有把总收益写成简单相加；但遗漏项使总目标不能完整闭合。
- E 排序：⚠️ `01` 单点安全风险最先、`02` 门禁次之合理；`05` 的高不确定性未优先且无证据解释。
